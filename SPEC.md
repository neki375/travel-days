Техническое задание: Telegram Mini App для учёта дней по странам

Версия 1.0 · MVP · Node.js + TypeScript + PostgreSQL

Я бы проектировал приложение как личный трекер путешествий, в котором пользователь отмечает въезд в страну, а при выезде закрывает поездку. Приложение автоматически считает дни пребывания, ведёт историю и показывает, сколько времени пользователь провёл в каждой стране.

Ключевое решение: одна открытая поездка обозначает текущую страну пользователя, а закрытые поездки сохраняют историю. Счётчик дней не хранится отдельно в базе — он рассчитывается из дат поездок, чтобы статистика не расходилась с историей.

1. Требования MVP
1.1. Основные сценарии

Въезд в страну

Пользователь нажимает «Отметить въезд», выбирает страну и дату. Приложение создаёт открытую поездку и начинает считать дни.

Выезд из страны

Пользователь нажимает «Отметить выезд». Текущая поездка закрывается выбранной датой, включая день выезда.

Статистика

Приложение показывает дни по странам за всё время, за текущий календарный год и за выбранный период.

История

Пользователь просматривает поездки, исправляет даты и удаляет ошибочные записи.

1.3. Правила подсчёта

Основное правило: день въезда и день выезда включаются в период пребывания.

days=exitDate−entryDate+1

Например:

Событие



Дата




Въезд



1 октября




Выезд



10 октября




Всего



10 дней

Для открытой поездки, если сегодня 27 октября и въезд был 1 октября, счётчик показывает 27 дней.

Необходимо также зафиксировать следующие правила:

В базе календарные даты хранятся как DATE, без преобразования в UTC.

Для одного пользователя разрешена только одна открытая поездка.

Две поездки одного пользователя не должны пересекаться по датам, даже если относятся к разным странам.

После выезда пользователь может указать следующую страну с той же датой въезда: например, выезд из страны A 10 октября и въезд в страну B 10 октября.

Если дата выезда в прошлом, открытая поездка должна считаться только до фактической даты выезда после её закрытия.

Исправление старых поездок должно пересчитывать всю статистику автоматически.

Последнее правило об одинаковой дате выезда и следующего въезда означает, что один календарный день может учитываться в обеих странах. Для личного трекера это допустимая модель; позднее можно добавить отдельный режим, если потребуется строгий учёт без двойного подсчёта.

3. Схема PostgreSQL

Для первой версии достаточно таблиц users, countries и trips. Статистику можно рассчитывать запросами к поездкам.

3.1. SQL-схема

CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    telegram_id BIGINT NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE countries (
    code CHAR(2) PRIMARY KEY,
    name TEXT NOT NULL
);

CREATE TABLE trips (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL
        REFERENCES users(id) ON DELETE CASCADE,
    country_code CHAR(2) NOT NULL
        REFERENCES countries(code),
    entry_date DATE NOT NULL,
    exit_date DATE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT trips_valid_dates CHECK (
        exit_date IS NULL OR exit_date >= entry_date
    )
);

-- Не более одной открытой поездки на пользователя.
CREATE UNIQUE INDEX trips_one_open_per_user
    ON trips(user_id)
    WHERE exit_date IS NULL;

-- Для истории и подсчёта дней по стране.
CREATE INDEX trips_user_entry_date_idx
    ON trips(user_id, entry_date DESC);

CREATE INDEX trips_user_country_entry_idx
    ON trips(user_id, country_code, entry_date);

countries нужно заполнить справочником ISO 3166-1 alpha-2. Это позволит использовать стабильные коды стран, а не названия, которые могут отличаться по языку.

3.2. Почему такая модель

telegram_id — внешний идентификатор Telegram; users.id — внутренний UUID.

exit_date IS NULL означает открытую поездку.

Отдельное поле status не требуется: статус можно вывести из даты выезда.

created_at и updated_at нужны для аудита изменений.

DATE для поездок защищает от сдвига календарного дня при преобразовании часовых поясов.

Индексы ускоряют загрузку истории и агрегацию статистики.

Важное ограничение: уникальный индекс защищает от двух открытых поездок, но не защищает от пересечений закрытых поездок. Проверку пересечений нужно реализовать в сервисе с транзакционной блокировкой пользователя либо через PostgreSQL exclusion constraint с подходящим диапазоном дат и расширением btree_gist.

Для MVP я бы сделал проверку пересечений на backend и добавил отдельные интеграционные тесты на параллельные запросы.

4. API-контракты

Все маршруты ниже имеют префикс /api/v1. Для MVP рекомендую REST API и JSON.

4.1. Авторизация

Frontend отправляет Telegram initData в заголовке:

Authorization: tma <initData>

Backend проверяет подпись и срок действия данных, после чего извлекает telegram_id и находит или создаёт пользователя.

Нельзя доверять telegram_id, переданному в JSON или query-параметре. Также нельзя использовать initDataUnsafe как доказательство подлинности без серверной проверки.

4.2. Список поездок

GET /api/v1/trips

Query-параметры:

from — необязательная дата начала фильтра.

to — необязательная дата окончания фильтра.

country — необязательный ISO-код страны.

limit и cursor — пагинация.

Пример ответа:

{
  "items": [
    {
      "id": "8f4a8a1b-8b2a-4d3a-a4c4-4f90f9f5a111",
      "country": {
        "code": "PH",
        "name": "Philippines"
      },
      "entryDate": "2026-10-01",
      "exitDate": null,
      "isOpen": true
    }
  ],
  "nextCursor": null
}

Все запросы фильтруются по текущему авторизованному пользователю. userId из запроса не используется для определения владельца.

4.3. Отметка въезда

POST /api/v1/trips

Запрос:

{
  "countryCode": "PH",
  "entryDate": "2026-10-01"
}

Ответ 201 Created:

{
  "id": "8f4a8a1b-8b2a-4d3a-a4c4-4f90f9f5a111",
  "countryCode": "PH",
  "entryDate": "2026-10-01",
  "exitDate": null,
  "days": 27,
  "isOpen": true
}

Поле days вычисляется на момент ответа. Для исторической поездки с датой выезда в будущем такой запрос в рамках базового MVP лучше отклонять, если нет отдельного сценария планирования поездок.

Возможные ошибки:

400 — некорректная дата или код страны.

409 — уже существует открытая поездка или обнаружено пересечение.

401 — отсутствует или не прошла проверку авторизация.

4.4. Отметка выезда

POST /api/v1/trips/:id/checkout

Запрос:

{
  "exitDate": "2026-10-27"
}

Ответ 200 OK:

{
  "id": "8f4a8a1b-8b2a-4d3a-a4c4-4f90f9f5a111",
  "countryCode": "PH",
  "entryDate": "2026-10-01",
  "exitDate": "2026-10-27",
  "days": 27,
  "isOpen": false
}

Backend должен проверить, что поездка принадлежит пользователю, ещё открыта и дата выезда не раньше даты въезда. Повторное закрытие поездки возвращает 409 Conflict.

4.5. Редактирование и удаление

PATCH /api/v1/trips/:id

{
  "entryDate": "2026-10-02",
  "exitDate": "2026-10-27"
}

DELETE /api/v1/trips/:id

Успешное удаление — 204 No Content.

Редактирование должно повторно проверять все ограничения по датам и пересечениям. Не следует разрешать изменять user_id или произвольные системные поля через этот API.

4.6. Справочник стран

GET /api/v1/countries?search=phil

Ответ:

  "items": [
    {
      "code": "PH",
      "name": "Philippines"
    }
  ]
}

Справочник можно загружать при запуске приложения и кэшировать на клиенте.

4.7. Статистика

GET /api/v1/statistics?from=2026-01-01&to=2026-12-31

Ответ:

{
  "from": "2026-01-01",
  "to": "2026-12-31",
  "countries": [
    {
      "countryCode": "PH",
      "days": 27
    },
    {
      "countryCode": "TH",
      "days": 15
    }
  ],
  "totalCountryDays": 42
}

totalCountryDays может превышать количество календарных дней периода, если даты поездок в разных странах пересекаются. Если требуется статистика общего количества уникальных календарных дней путешествий, это должна быть отдельная метрика.

Для статистики учитываем дни пересечения поездки с запрошенным периодом. Если exit_date IS NULL, конец периода определяется как минимум между текущей датой и to.

4.8. Единый формат ошибок

Рекомендую использовать один формат для всех ошибок:

{
  "error": {
    "code": "TRIP_OVERLAP",
    "message": "Trip dates overlap with another trip"
  }
}

Основные коды: VALIDATION_ERROR, UNAUTHORIZED, TRIP_NOT_FOUND, TRIP_ALREADY_CLOSED, TRIP_OVERLAP, OPEN_TRIP_EXISTS, INTERNAL_ERROR.

5. Бизнес-логика и реализация на TypeScript

Я бы разделил логику на три уровня:

Route / Controller — HTTP-запрос, валидация входа и формирование ответа.

Service — правила въезда, выезда, проверка пересечений, транзакции.

Repository — SQL-запросы через Drizzle ORM.

Пример расчётного модуля:


/**
 * Даты в формате YYYY-MM-DD.
 * Считает обе граничные даты включительно.
 */
export function calculateDays(
  entryDate: string,
  exitDate: string,
): number {
  const entry = parseDate(entryDate);
  const exit = parseDate(exitDate);

  const difference = exit.getTime() - entry.getTime();

  if (difference < 0) {
    throw new Error("EXIT_BEFORE_ENTRY");
  }

  return Math.floor(difference / 86_400_000) + 1;
}

function parseDate(value: string): Date {
  if (!/^\d{4}-\d{2}-\d{2}$/.test(value)) {
    throw new Error("INVALID_DATE");
  }

  const [year, month, day] = value.split("-").map(Number);
  const date = new Date(Date.UTC(year, month - 1, day));

  if (
    date.getUTCFullYear() !== year ||
    date.getUTCMonth() !== month - 1 ||
    date.getUTCDate() !== day
  ) {
    throw new Error("INVALID_DATE");
  }

  return date;
}

Здесь UTC используется только для арифметики календарных дат — не для хранения времени въезда. Это позволяет корректно обрабатывать границы месяцев, годов и високосные годы.

Для открытой поездки перед вызовом функции следует подставлять текущую дату в формате YYYY-MM-DD. Её нужно получать на backend, а не принимать от клиента. Для этого проекта я бы отдельно зафиксировал единую настройку бизнес-часового пояса: например, UTC для личного календаря либо выбранный пользователем часовой пояс. Нельзя незаметно менять дату в зависимости от часового пояса сервера.

Сервис поездок

Основные методы:

interface TripsService {

Типы CheckInInput, UpdateTripInput и остальные следует выводить из Zod-схем, чтобы валидация и TypeScript-типы не расходились.

Важный нюанс транзакций

Операция checkIn() должна быть атомарной:

Заблокировать строку пользователя в транзакции (SELECT ... FOR UPDATE).

Проверить отсутствие открытой поездки.

Проверить пересечения с существующими поездками.

Создать запись.

Зафиксировать транзакцию.

Так два параллельных запроса не смогут одновременно создать две открытые поездки. Аналогичный принцип нужен для изменения и закрытия поездки.

10. Уточнения MVP

Этот раздел устраняет противоречия и неоднозначности разделов 1–9. При расхождении приоритет у этого раздела.

10.1. Пересечения поездок

Поездки A и B одного пользователя конфликтуют, если A.entry < B.exit и B.entry < A.exit. Для открытой поездки exit = +∞.

Следствия:
- Общим может быть только граничный день: выезд из A 10 октября и въезд в B 10 октября разрешены, день учитывается в обеих странах.
- Однодневная поездка (entry = exit) разрешена, если её день совпадает с границей соседних поездок. Транзит A → B → C за один день допустим.
- Однодневная поездка внутри другой поездки (не на границе) — конфликт.
- Никакая поездка не может начинаться позже даты въезда открытой поездки.

Проверка выполняется в сервисе внутри транзакции (READ COMMITTED) после SELECT ... FOR UPDATE строки пользователя. Дополнительно БД страхует:
- уникальный частичный индекс trips_one_open_per_user;
- exclusion constraint (btree_gist) по tsrange(entry_date, coalesce(exit_date, 'infinity'), '()') для поездок с exit_date IS NULL OR exit_date > entry_date. Однодневные поездки проверяются только сервисом.

Нарушение ограничений БД возвращается как 409 OPEN_TRIP_EXISTS / TRIP_OVERLAP.

10.2. Часовой пояс и «сегодня»

Frontend передаёт заголовок X-Timezone с IANA-зоной (например, Asia/Manila). Backend проверяет её и вычисляет текущую дату в этой зоне. Без заголовка или при некорректном значении используется UTC. Дата никогда не принимается от клиента напрямую.

«Сегодня» используется для подсчёта дней открытой поездки, проверки будущих дат и определения текущего года.

10.3. Допустимые даты

- Формат YYYY-MM-DD, реальная календарная дата.
- Не раньше 1900-01-01.
- entryDate и exitDate не позже «сегодня» во всех операциях (создание, выезд, редактирование).
- exitDate >= entryDate.

10.4. Единый формат поездки

Все эндпоинты возвращают поездку в одном формате:

{
  "id": "uuid",
  "country": { "code": "PH", "name": "Philippines" },
  "entryDate": "2026-10-01",
  "exitDate": null,
  "days": 27,
  "isOpen": true
}

days вычисляется на момент ответа; для открытой поездки — до «сегодня».

10.5. Изменения API

POST /api/v1/trips принимает необязательный exitDate. Без него создаётся открытая поездка (въезд), с ним — закрытая историческая поездка. Правила пересечений одинаковы.

GET /api/v1/trips/current возвращает { "trip": Trip | null } — текущую открытую поездку.

GET /api/v1/trips:
- сортировка entryDate DESC, id DESC;
- from/to выбирают поездки, пересекающие период;
- limit по умолчанию 50, максимум 100;
- cursor — непрозрачная строка из nextCursor.

PATCH /api/v1/trips/:id:
- допустимые поля: countryCode, entryDate, exitDate; нужно хотя бы одно;
- отсутствующее поле не меняется;
- exitDate: null переоткрывает поездку, если это не нарушает ограничений;
- проверяются все правила 10.1 и 10.3 (без учёта самой редактируемой поездки).

POST /api/v1/trips/:id/checkout: exitDate обязателен; frontend по умолчанию подставляет «сегодня».

GET /api/v1/statistics:
- from и to необязательны; без from — с начала истории, без to — по «сегодня»; в ответе отсутствующая граница возвращается как null;
- from > to — 400;
- для каждой поездки учитывается пересечение [max(entry, from), min(exit ?? сегодня, to)];
- страны сортируются по days DESC, затем по code.

Все входные схемы строгие: неизвестные поля (в том числе userId) — 400 VALIDATION_ERROR.

10.6. Ошибки

Код — HTTP-статус:
- VALIDATION_ERROR — 400 (формат, неизвестная страна, будущая дата, выезд раньше въезда); может содержать details.
- UNAUTHORIZED — 401.
- TRIP_NOT_FOUND — 404; также для чужой поездки, чтобы не раскрывать её существование.
- NOT_FOUND — 404 для неизвестного маршрута.
- OPEN_TRIP_EXISTS, TRIP_OVERLAP, TRIP_ALREADY_CLOSED — 409.
- INTERNAL_ERROR — 500, без деталей реализации.

10.7. Авторизация

initData проверяется по HMAC-SHA-256 с токеном бота. Максимальный возраст auth_date — 24 часа (переменная INIT_DATA_MAX_AGE_SECONDS). initData без поля user отклоняется. Пользователь создаётся через INSERT ... ON CONFLICT (telegram_id) DO NOTHING.

10.8. Справочник стран и язык

UI только на русском, без i18n-фреймворка. countries.name хранится на английском. Клиент отображает названия через Intl.DisplayNames('ru') и ищет по закэшированному справочнику. Справочник — ISO 3166-1 alpha-2 плюс XK (Косово).

10.9. Бот

Отдельный процесс apps/bot на grammY с long polling. В MVP только /start с кнопкой открытия Mini App, без доступа к БД.

10.10. Расчёт дней

day-calculator не имеет параметра «режим расчёта»: в MVP режим один (обе даты включительно). Статистика агрегируется чистыми функциями TypeScript по поездкам, пересекающим период.
